# Проверки Python-версии

Проверенная среда: Python 3.13.18, SQLite 3.53.1, Windows. Зависимости закреплены в uv.lock и экспортированы с хешами в requirements-файлы. Автоматическая проверка GitHub повторяет тесты на Ubuntu и Windows.

```sh
python -m ruff check .
python -m ruff format --check .
python -m pytest -q
python -m router_bot demo
python -m pip_audit -r requirements.txt --disable-pip
```

Подменённый клиент проверяет транспорт, а не наличие настоящего доступа; тесты правил не запускают вычислитель / интерфейс Google.

## Перед настоящим запуском на копии

1. Подтвердить владельцев доступа, смысл Checked и G/H, VIP, регламент и календарь сбора, политику контактов.
2. Проверить service account на копии с правильными title/sheetId; сохранить заголовки, легенду и «2ка». Новые столбцы не нужны и не создаются.
3. Проверить первый и повторный `/sync`, ID в отдельной БД, ручные изменения, сортировку, удаление / переименование номера, сбой Google и возобновление очереди.
4. Два тестовых сотрудника проходят цикл, отзыв прав и личные / групповые чаты; ответственный получает тестовую сводку после /start.
5. `/repair_colors` на копии: все статусы, ? / Неизвестно, заголовок, пустая и новая строка, Checked, постороннее оформление. Проверить смену московского дня: бот вычисляет срок в SQLite и обновляет D после успешного обмена.
6. Восстановить копию в новый путь с `pause-sync`, сравнить с таблицей до включения отправки, проверить передачу полномочий.

## Границы гарантий

- История и расширенные данные находятся в отдельной SQLite. Таблица без новых столбцов отражает только A:J. Номер Inv. № должен сохраняться: массовое ручное перенумерование автоматически не угадывается.
- Изменения физического состояния не выводятся из цвета, Checked или Checkout. Переходы с недостающими фактами остаются на уточнении; администратор оформляет их предметно в карточке.
- В SQLite операции атомарны. Общей транзакции с Google нет, последняя одновременная правка / сортировка между чтением и записью остаётся возможной. Выявленные расхождения блокируются.
- Без дополнительных столбцов формулы цветов видят Status, а не скрытый срок из SQLite. Во время остановки бота / недоступности Google новая вычисленная просрочка появится в D после возобновления.
- Telegram sendMessage не имеет ключа идемпотентности отправителя. После таймаута фактически доставленное сообщение может повториться; после подтверждённой отправки логическая сводка не дублируется. Состояние роутера при ошибке доставки не меняется.
- Update_id, шаг диалога, предметная операция и исходящий ответ фиксируются одной SQLite-транзакцией. Сбой до фиксации позволяет повторить обновление; после фиксации повтор не продвигает диалог и не создаёт вторую операцию, а неотправленный ответ остаётся в очереди. Доставка сообщений Telegram остаётся как минимум однократной, без гарантии отсутствия повторов после неопределённого сетевого результата.
- Старые сообщения Telegram / скачанные CSV нельзя отозвать у пользователя; новое чтение и действия после отзыва запрещаются. Сроки хранения копий / истории Google / свободных примечаний настраивает владелец отдельно.
- Один процесс и небольшая таблица; веб-панели, студенческого кабинета и сложной инфраструктуры нет. Перенос не запускает настоящую кампанию и не меняет исходник по догадкам.
