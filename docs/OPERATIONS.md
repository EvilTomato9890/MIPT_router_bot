# Эксплуатация и передача

## Обычная работа

Наблюдатель видит поиск, карточки, историю, отчёты и экспорт. Оператор добавляет, выдаёт, принимает, фиксирует утрату / обнаружение и техническое состояние, действует в очереди сбора. Администратор дополнительно управляет доступом, VIP, продлениями, исключениями, списанием, исправлениями, кампаниями, импортом и раскраской. В группах бот не выдаёт записи и контакты.

Перед выдачей выберите свободный исправный роутер, проверьте комплект. Получатель — человек либо организация; для организации предусмотрен ответственный человек, учебные поля не спрашиваются. Неизвестные необязательные сведения оставляйте знаком `-`. Telegram ID заполняйте только при подтверждении. Бот предупредит о похожем получателе или совпадении места, но имя само по себе не идентифицирует человека.

При приёме сверяйте инвентарный номер, комплект и физическое наличие. При отсутствии проверки выбирайте «Нужна проверка». Блок питания отмечается независимо: роутер можно принять без него, недостающий БП будет виден в отчёте. Неисправный / непроверенный возврат нельзя снова выдать до проверки. Причина и повреждения попадут в историю.

При утрате укажите обстоятельства; срок сам по себе не делает устройство утерянным. Обнаружение сначала фиксируется как факт. Администратор затем решает, оставлен ли роутер у прежнего получателя или физически принят. Списание и закрытие нерешённой выдачи требуют отдельного подтверждения. Для исправления ошибочной последней операции в карточке укажите ID события из истории. Если есть последующие события или операция затрагивает связанные объекты, оформите явные предметные действия с причиной вместо отката.

## Кампания сбора

Администратор создаёт проект: набор / учебный год, начало, конечный срок, ID ответственных сотрудников, место, часы и инструкцию. До запуска показывается полный список кандидатов и список для уточнения. Все ответственные должны иметь права минимум оператора и открыть личный чат с ботом.

Автоматически подходят только подтверждённые выдачи людям нужного набора / года с подтверждённым типом места «Комната». Организации, общие помещения, неподтверждённое место, неизвестные получатели и неразмеченные наборы не включаются автоматически. В просмотре кампании можно явно включить действующую выдачу по инвентарному номеру с причиной.

Очередь сначала показывает просрочку, затем сроки, этаж, секцию и естественный порядок мест. Администратор может задать приоритет и оператора. «Принят» открывает обычный диалог физического приёма. «Не застали», «Связались», «Проблема» и «Следующий» записывают только результат обхода. «Согласована другая дата» не продлевает срок: администратор оформляет продление в карточке. Возвращённое исчезает из текущей очереди и остаётся в итогах.

При индивидуальном подтверждённом сроке позже конечного срока кампании используется более поздняя дата. VIP не меняет очередь. Отдельное исключение с причиной действует до даты пересмотра; после её истечения выдача снова видна для сбора. Дополнительное исключение только из конкретной кампании хранится в составе этой кампании с причиной.

Начальные настройки напоминаний — 14, 7, 1, 0 дней, затем ежедневная просрочка; это предложенные настройки, не регламент общежития. Настраиваются через `.env`, время — `Europe/Moscow`. Кампанию можно приостановить в её настройках. Сводки получают только назначенные сотрудники с актуальными правами. Студентам сообщения не отправляются.

## Один процесс и постоянный диск

`npm start` использует long polling. Входящие порты и веб-панель не нужны; требуется исходящий HTTPS к Telegram, Google OAuth и Sheets API. Файл блокировки рядом с БД предотвращает случайный запуск второго процесса на той же БД. Если предыдущий PID действительно отсутствует, устаревшая блокировка снимается при запуске. Не запускайте несколько разных копий БД с одним токеном: Telegram polling у них общий.

Пример Linux systemd после размещения проекта в `/opt/mipt-router-bot` и создания отдельного системного пользователя `routerbot`:

```ini
[Unit]
Description=Dorm 7 router inventory bot
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=routerbot
WorkingDirectory=/opt/mipt-router-bot
ExecStart=/usr/bin/node --env-file=.env src/main.mjs
Restart=on-failure
RestartSec=10
UMask=0077
NoNewPrivileges=true

[Install]
WantedBy=multi-user.target
```

Уточните путь к Node на сервере. `.env`, `secrets`, `data` и `backups` доступны только пользователю службы и назначенному ответственному. Хранилище должно быть постоянным; не помещайте рабочую SQLite на сетевую папку или синхронизируемый облачный диск. Для Windows можно использовать один процесс `npm start` в рабочем каталоге; постоянный запуск назначается штатным планировщиком от отдельной учётной записи без одновременных копий.

Если для токена уже существует webhook, бот останавливается с понятным сообщением и не удаляет его автоматически. После согласованного переноса отключите webhook методом Telegram `deleteWebhook` с `drop_pending_updates=false`; не публикуйте URL с токеном в логах или истории общего терминала. Затем повторите запуск. Смена транспорта не должна удалять ожидающие обновления.

## Резервное копирование

Процесс раз в московский день создаёт согласованную онлайн-копию через `node:sqlite.backup`, по умолчанию сохраняет 14 дневных копий в `BACKUP_DIR`. При ошибке выдаёт техническое предупреждение без данных людей. Бэкапы также содержат персональные данные: права доступа, срок хранения и отдельная защищённая копия на другом носителе обязательны для ответственного.

Ручная проверенная копия:

```sh
npm run backup
npm run backup -- ./backups/before-upgrade.sqlite
```

Команда не создаёт копию несуществующей БД и не перезаписывает исходную БД. После копирования выполняется `PRAGMA integrity_check`. Не копируйте только основной `.sqlite` во время работы средствами файлового менеджера: актуальные данные могут находиться в WAL.

### Восстановление

1. Остановите службу, убедитесь, что нет другого процесса с тем же токеном.
2. Сохраните повреждённые `.sqlite`, `-wal`, `-shm`, `.lock` в отдельный закрытый каталог для разбора. Не удаляйте их вслепую.
3. Возьмите проверенную копию и восстановите её в **новый путь**, например `data/restored.sqlite`; задайте этот путь в `DB_PATH`.
4. Запустите сначала с `SHEETS_MODE=disabled`. Проверьте карточки, количество оборудования, историю, роли и кампании. Не используйте «переимпортировать всё заново» как замену восстановлению истории.
5. Восстановленная копия старее Google Sheets. До возобновления отправки сделайте повторный просмотр `/sync` в режиме google и разберите различия. Чтобы исключить автоматическую отправку при первом старте, до запуска с google оставьте процесс остановленным и на копии БД переведите outbox в blocked через SQLite (`UPDATE outbox SET state='blocked'`). Затем запустите и явно согласуйте `/sync`. Сначала проверьте этот порядок на тестовой копии.
6. Сверьте последние предметные события с бумажным / внешним учётом, проверьте дату последнего бэкапа и актуальных ответственных. При спорных выдачах не запускайте массовое восстановление строк поверх таблицы.

Резервная копия содержит задания и отметки отправки на момент её создания. Сообщения, отправленные после этого момента, могут повториться после восстановления старой копии. Это отдельная граница гарантий, не повтор учётных операций.

## Контакты и секреты

`CONTACT_RETENTION_DAYS` — срок после закрытия выдачи, независимо от срока истории оборудования; начальное значение 365 дней, `0` выключает автоматическую очистку. Закрытая выдача с неизвестной фактической датой не получает вымышленную дату ради очистки, её данные требуют отдельного решения администратора. Наследуемые пометки вне действующих выдач также требуют разбора, их происхождение неизвестно. Не помещайте контакты в причины операций и технические комментарии, если планируете автоматическую очистку структурированных контактов.

Старые копии БД и история Google могут сохранять прежние контакты: владелец отдельно устанавливает срок хранения резервных копий и политику самой таблицы. Снимки сравнения не удаляются произвольно: они нужны для обнаружения ручных конфликтов; при возврате и подтверждённой отправке текущее представление перестаёт содержать контакты получателя. Устаревшие диалоги и просмотры удаляются процессом после 30 минут.

При компрометации токена перевыпустите его через BotFather, при компрометации Google-ключа отзовите старый ключ в Cloud. Секреты меняются в конфигурации, никогда в коммитах. Ротация ключа не требует создания новой БД.

## Передача новому ответственному

1. Создайте резервную копию и проверьте восстановление на отдельном пути.
2. Передайте репозиторий, версию Node, схему, рабочую конфигурацию и секреты по защищённому каналу.
3. Старый администратор назначает нового по числовому ID в «Настройки → Доступ». Новый открывает чат, проверяет административные команды и назначенных сотрудников.
4. Обновите владельцев токена / сервисного аккаунта / таблицы, права файлов, адреса ответственных и конфигурацию службы. Новые ID кампаний меняются через настройки кампании.
5. Новый администратор отзывает доступ прежнего после проверки. Последний администратор не может быть удалён. `BOOTSTRAP_ADMIN_ID` используется только один раз для новой БД, перезапуск не возвращает отозванные права.
6. Проверьте тестовую выдачу на отдельном оборудовании / копии, `/sync`, восстановление раскраски на копии и получение сводки сотрудником. Зафиксируйте регламент сбора и нерешённые наследуемые данные.
